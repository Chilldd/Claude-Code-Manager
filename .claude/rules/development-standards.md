# 工程规范

## 设计原则
- **单一职责**：一个模块/函数只做一件事。超过 300 行的文件或同时操作多个抽象层次的函数应考虑拆分
- **关注点分离**：业务逻辑与平台代码分离，纯计算与 I/O 分离
- **最小依赖**：模块间禁止循环依赖，不依赖不需要的东西
- **防御性编程**：外部输入不可信（文件、网络、用户参数），必须校验和兜底
- **DRY**：重复的逻辑提取为公共函数，但不要为"可能复用"而过早抽象

## Git
- 直接在 master 提交（需隔离时用 worktree）
- Commit 格式：`<type>: <description>` — type: `feat`、`fix`、`refactor`、`docs`、`test`、`chore`
- 一个 commit 一个逻辑变更，禁止混杂不相关的改动

## Code Review
- 所有 PR 必须 review 后合入
- 检查要点：错误处理、测试覆盖、数据安全
- CI 必须通过

## CI/CD
- PR 流水线：`cargo check` → `cargo test` → `cargo clippy`
- 发布流水线：升版本号 → 打 tag → 构建产物
- 新增依赖不能有 `cargo audit` 失败

## Changelog
- `CHANGELOG.md` 随版本更新，格式：`## [版本号] - YYYY-MM-DD`
- 分节：Added、Changed、Fixed、Removed
- 只记录用户可见变更

## 依赖管理
- 锁定 major.minor 版本（如 `"2"`、`"0.7"`），禁止 `"*"`
- 加新依赖前先确认现有依赖是否已覆盖需求

## 错误处理
- 禁止静默吞噬错误（IO/持久化/序列化等关键路径禁止 `let _ = ...`）
- 日志格式：`[模块名] 描述: {错误详情}`

## 测试
- 纯函数（无 I/O、无外部依赖）必须有单元测试
- CRUD 操作和数据损坏恢复路径应当测试

## 数据安全
- JSON 反序列化失败时：先备份原文件、打日志、再返回安全默认值
- 禁止 `unwrap_or_default()` 直接接解析结果（导致损坏数据被静默覆盖）
